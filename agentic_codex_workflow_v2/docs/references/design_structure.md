# Agentic engineering for coding

> **可复现、可验证、可回滚、可断点重续、可持续演进、上下文不腐烂。**

- **局部操作与局部判断，下放给 agent**
- **全局制度、不可违背的不变量、验证与演进机制，上提到系统设计**
- **四个注意点**：
  A. 代码生成是强项不是主问题，agent 运行系统才是主问题
  B. 任何能被程序化正确处理的事，都不该继续留给 LLM
  C. 任务推进必须依赖外部证据，而不是会话内自述
  D. 上下文、状态、意图、验证、回滚都必须外部化并可重建

---

## **全局核心不变量**。

它们不是某个框架的技巧，而是一个 agent 开发系统是否成立的判据。

---

### 核心不变量 1：**把“机械正确性”从 LLM 中剥离出来**

这是最根的原则。

GSD 讲得非常清楚：
如果某件事可以被 `if-else` 正确处理，那么它就不应该交给 LLM；应该交给确定性代码。LLM 负责 judgment work，确定性层负责 git、状态迁移、文件解析、上下文装配、静态验证等机械工作。

这条原则的本质是：

**不要让概率系统承担制度职责。**

因为一旦你让 LLM 负责：

- 当前在哪个任务
- 应该读哪些文件
- git 应该怎么回滚
- 当前上下文是否过期
- 哪个状态可以推进到下一个状态

那系统很快就会变成“偶尔工作、不可解释、不可恢复”。

所以第一个核心不是“会不会 prompt”，而是：

**系统要明确划分：什么是判断，什么是流程控制。**

这是后面一切模块设计的起点。

---

### 核心不变量 2：**状态必须外部化，不能寄存在会话里**

GSD 整个系统成立的前提之一，就是状态不在对话里，而在磁盘和 git 里：
当前 milestone / slice / task、summary、continue file、branch、checkpoint，全部可被重建。

这条原则的本质是：

**会话不是状态容器，会话只是计算过程。**

如果状态在会话里，结果就一定会出现：

- 断了就丢
- 换个 agent 就接不上
- 历史决策不可查
- 进度不可重建
- 系统无法稳定自动化

所以“可断点重续”“可持续演进”的前提不是多会写总结，而是：

**所有关键状态都必须有外部、可解析、可版本化的表示。**

这也是为什么 continue file、task artifacts、summary、context.md 这些不是“辅助文档”，而是系统状态的一部分。

---

### 核心不变量 3：**上下文必须是“按任务装配”的，而不是“自然累积”的**

GSD 的 anchor pruning 和 pre-assembled context，systematicls 的“研究与实现分离”“上下文膨胀是大问题”，其实讲的是同一件事：
**上下文不是越多越好，越多通常越坏。**

这条原则的本质是：

**上下文是依赖注入，不是聊天记录。**

一个成熟系统的上下文应该满足 4 个要求：

1. **只给当前任务需要的内容**
2. **依赖信息优先于历史噪音**
3. **旧信息要能被压缩，但不能压缩到失真**
4. **上下文必须可重建，而不是靠“上个 session 聊过”**

GSD 的做法是：

- 每个 task 一个干净锚点
- 当前任务只看到当前 plan + 上游摘要
- 用层级 summary 做压缩
- 明确禁止“summary of summary”递归失真

systematicls 的做法是：

- 研究和实现分会话
- 每个 contract 一个新会话
- 用规则指定该读什么，而不是让 agent 自己猜

所以“上下文不腐烂”的本质不是写更多记忆，而是：

**把上下文从“堆积型”改成“装配型”。**

---

### 核心不变量 4：**任务必须以“可观察结果”定义，而不是以“步骤完成”定义**

GSD 的 must-haves、truths / artifacts / key links、4-tier verification；
systematicls 的 tests / screenshots / contract；
它们共同指向同一个更底层的原则：

**任务的结束条件必须是外部可验证的结果，而不是 agent 自述“我做完了”。**

这条原则的本质是：

**系统不能相信过程，只能相信结果证据。**

所以一个任务定义如果长这样：

- “实现认证”
- “加上错误处理”
- “把登录流程做好”

这在 agent 系统里几乎等于没定义。

而有效的定义应该能落到：

- 哪些行为必须为真
- 哪些文件必须存在且有实质实现
- 哪些 wiring 必须连上
- 哪些测试必须通过
- 哪些 screenshot / 行为需要验证
- 哪些人类检查是最后兜底，而不是默认入口

这就是为什么你提到“可验证”是核心，我完全同意，而且要更尖锐一点说：

**没有终止条件的任务，不是任务，只是意图。**

---

### 核心不变量 5：**变更必须天然可逆，否则系统不具备真实自治能力**

GSD 的 branch / checkpoint / squash / rollback / revert / fix 分支，不只是 git hygiene，而是 agent 系统的生存条件。

这条原则的本质是：

**只有可逆，才能放权。**

很多人说“让 agent 自主执行”，但如果：

- 没有 checkpoint
- 没有 slice 级 branch
- 没有单元化 revert 粒度
- 没有 fix flow
- 没有状态与代码版本对应关系

那其实不是自治，而是赌博。

所以“可回滚”不是工程质量细节，而是 agent delegation 的先决条件。
你不给系统可逆性，就不可能安全地下放执行权。

---

### 核心不变量 6：**系统必须把“演进”设计成常态，而不是把“正确一次”当目标**

Harrison 那篇说 bottleneck 已经从 implementation 转向 review；
systematicls 说规则和 skills 会不断膨胀、冲突，需要定期清理；
GSD 说总结、UAT、fix tasks、continue flow 都要成为自然机制。

这条原则的本质是：

**agent 系统不是一次性交付系统，而是持续校正系统。**

因此你要设计的不是：

- 如何一次把需求讲清楚
- 如何一次生成完美结果

而是：

- 如何低成本发现偏差
- 如何低成本修复偏差
- 如何把偏差反馈进规则、skills、contracts、上下文
- 如何让系统在更多轮次后更稳定，而不是更乱

所以“可持续演进”不是额外要求，而是系统是否成熟的核心标志。

---

# 二、把这些核心不变量压缩成一句总纲

## **Agent 开发系统的本质，不是“让模型会写代码”，而是“构造一个外部化状态、按任务装配上下文、以可验证结果推进、并且天然可逆的自治执行系统”。**

这句话里每个词都不可删：

- **外部化状态** → 可恢复
- **按任务装配上下文** → 不腐烂
- **可验证结果推进** → 不假完成
- **天然可逆** → 敢放权
- **自治执行系统** → 不靠人时刻盯梢

这才是全局核心。

---

# 三、从核心不变量推出系统模块：不是随便分，而是“必须存在”的模块

一个完整的 agent 开发系统，至少必须有 8 个模块。这 8 个不是产品菜单，而是系统拓扑。

---

## 模块 1：**意图与决策模块（Intent / Decision Module）**

### 它解决什么

这是整个流程中最重要的内容，把“用户真正想要什么”和“灰色地带做了什么选择”固定下来，避免后续漂移。

### 它为什么是必需的

GSD 的 discussion phase 就是在做这件事：
agent 不直接开工，而是先找 gray areas，和用户讨论，产出 `context.md`，并把决策注入后续所有阶段。

Harrison 那篇也在讲同样的问题：
原型出来以后，reviewer 必须知道“哪些部分是故意的，哪些只是 accidental”，所以“PRD 死了，但表达 intent 的文档更重要”。

### 它的本质职责

不是写 PRD，而是维护四类信息：

1. **目标意图**：要达成什么用户可见结果
2. **边界约束**：做/不做什么、延期什么、优先级如何
3. **技术/架构规范**：使用什么技术、遵循哪些架构规范、性能、生命周期
4. **决策记录**：灰区里选了哪条路，为什么

### 这模块的设计判据

一个方法如果不能把“意图”和“选择”沉淀成可被后续执行读取的工件，那它不成熟。

---

## 模块 2：**规划与分解模块（Planning / Decomposition Module）**

### 它解决什么

把模糊目标分成可以独立推进、独立验证、独立演进的工作单元。

### 它为什么是必需的

GSD 的 3-level hierarchy 不是组织术语，而是上下文控制与验证控制的基础：
milestone 是可发布版本，slice 是可演示垂直能力，task 是单会话可完成单元。

boundary map 则负责定义产出/消费关系，防止后续 slice 基于幻想接口继续开发。

### 它的本质职责

1. **定义最小可完成单元**
2. **定义依赖关系**
3. **定义每层的压缩方式与验收方式**

### 这模块的设计判据

好的分解不是“列 TODO”，而是满足：

- 单元边界稳定
- 可观察
- 可验证
- 可压缩
- 可接力

如果一个方法拆出来的单元需要跨 3 个 session 才能看出结果，那这个分解是失败的。

---

## 模块 3：**状态模块（State Machine / Workflow State Module）**

### 它解决什么

回答“系统现在在哪、下一步是什么、哪些完成了、哪些中断了、是否允许推进”。

### 它为什么是必需的

GSD 把 state derivation、next task、complete task、complete slice 都交给确定性层处理。

### 它的本质职责

1. **当前位置**
2. **合法迁移**
3. **完成条件**
4. **中断恢复点**
5. **状态与工件的一致性**

### 这模块的设计判据

如果当前进度必须靠“翻聊天记录”“问 agent 你做到哪了”才能知道，那状态模块就是缺失的。

这模块是你后续重点研究的核心之一，因为它决定了系统是否真正“自治”。

---

## 模块 4：**上下文与记忆模块（Context Assembly / Memory Module）**

### 它解决什么

回答“当前任务该看到什么，不该看到什么”。

### 它为什么是必需的

GSD 的 anchor pruning、pre-assembled context、hierarchical summaries；
systematicls 的 research/implementation 分离、每 contract 新会话、CLAUDE.md 作为规则目录；
都属于这个模块。

### 它的本质职责

1. **任务级上下文装配**
2. **依赖摘要注入**
3. **无关历史裁剪**
4. **记忆压缩**
5. **规则/skills 按场景路由**

### 这里要特别说明 skills 的位置

我认为 **skills 不是一级核心模块，而是上下文模块中的“方法注入子系统”**。

因为 skills 的本质不是“存知识”，而是：

- 在某类情境下，向 agent 注入某套可复用方法
- 让 agent 少探索、多复用
- 把“做事方式”从人脑迁移到外部工件

systematicls 说得很直接：
rules 更适合编码偏好，skills 更适合编码配方/方法。

所以以后我们分析 skills 时，不应该把它当孤立模块，而应把它放在：

**“上下文装配系统如何根据场景给 agent 注入方法学”** 这个位置来分析。

---

## 模块 5：**执行模块（Execution Harness Module）**

### 它解决什么

让 agent 在受控环境里完成真实工作，而不是停留在文本层。

### 它为什么是必需的

GSD 里 agent 不是抽象思考者，而是真实执行者：写代码、跑命令、验证行为。
同时 deterministic tools 屏蔽掉机械操作，把 agent 资源留给 judgment work。

systematicls 也强调不要搞 24 小时漂移长会话，而要“每个 contract 一个新会话”，由编排层创建新任务。

### 它的本质职责

1. **提供可操作环境**
2. **约束 agent 的工具边界**
3. **控制单次执行粒度**
4. **把机械动作接口化**

### 这模块的设计判据

执行模块的成熟度，不看能不能跑 bash，而看：

- agent 是否在做不该做的机械思考
- 会话粒度是否稳定
- 工具是否帮它减少无意义 token 消耗
- 执行是否总能映射回状态模块

---

## 模块 6：**验证模块（Verification / Evaluation Module）**

### 它解决什么

回答“系统凭什么认为这个任务真的完成了”。

### 它为什么是必需的

这部分在你给的材料里几乎是共识：

- GSD：must-haves、truths/artifacts/key links、4-tier ladder
- systematicls：tests、screenshots、contract、禁止提前终止
- Harrison：瓶颈变成 review，本质上也在说明验证系统才是吞吐瓶颈

### 它的本质职责

1. **定义终止条件**
2. **采集证据**
3. **分层验证**
4. **决定是否推进/返工**
5. **把验证结果反馈给状态模块**

### 这模块是全局里最重要的“闸门”

我甚至会说：
**一个 agent 系统，最终不是由“规划能力”定义的，而是由“验证闸门的质量”定义的。**

因为规划错一点还能修，验证弱就会把错的东西持续推进下去。

---

## 模块 7：**版本与可逆模块（Versioning / Reversibility Module）**

### 它解决什么

回答“如果 agent 做错了，如何最小代价撤销”。

### 它为什么是必需的

GSD 的 slice branch、task checkpoint、squash merge、revert、fix flow，已经把这个模块写得非常清楚。

### 它的本质职责

1. **隔离变更**
2. **生成撤销粒度**
3. **维护清晰历史**
4. **让错误修复成为标准流程**

### 这模块的设计判据

如果一个系统只能“继续改”，不能“准确退回”，它就还不适合高自治。

---

## 模块 8：**恢复与演进模块（Recovery / Evolution Module）**

### 它解决什么

回答“中断后如何续、长期使用后如何不劣化”。

### 它为什么是必需的

GSD 的 continue file 解决断点重续；
systematicls 的规则/skills 会膨胀并冲突，所以要定期清理；
Harrison 的观点则说明 review 会成为持续性瓶颈，因此系统必须能演化其流程而不是只生成更多东西。

### 它的本质职责

1. **中断恢复**
2. **fix task 闭环**
3. **规则/skills 整理**
4. **系统性偏差回灌**
5. **流程持续优化**

### 这模块很容易被忽视

但实际上它决定系统是：

- 越用越强
  还是
- 越用越乱

---

# 四、把 8 个模块再压一层：四层设计没错，但还不够“可设计”

- 意图层
- 上下文层
- 执行层
- 反馈层

我认为这四层是**顶层视角**，是对的。
但如果要指导系统设计，必须继续往下切成模块。

我会这样映射：

### 1. 意图层

包含：

- 意图与决策模块
- 规划与分解模块

### 2. 上下文层

包含：

- 状态模块
- 上下文与记忆模块
- skills / rules 子系统

### 3. 执行层

包含：

- 执行模块
- 版本与可逆模块

### 4. 反馈层

包含：

- 验证模块
- 恢复与演进模块

这样就能从“理念分层”落到“系统模块”。

# 五、以后怎么用这些核心来判断一个方法是不是靠谱

你要的是“能指导系统设计的核心”，那就必须能拿来做判断。
我给你一个极简判别器：

## 任何一个新方法、新框架、新说法，都问这 7 个问题：

1. **它把哪些职责交给 LLM，哪些职责交给确定性系统？**
   如果边界不清，就是风险。

2. **它的状态存在哪里？是否可重建？**
   如果主要存在对话里，就不可靠。

3. **它如何避免上下文腐烂？**
   如果靠长会话自然累积，基本会劣化。

4. **它的任务终点是什么？谁来判定完成？**
   如果是 agent 自述完成，那就不成立。

5. **它的验证证据是什么？是否优先依赖机器可验？**
   如果默认靠人 check，吞吐会崩。

6. **它的回滚粒度是什么？错误如何撤销？**
   如果没有天然可逆性，就不能高自治。

7. **它如何在长期使用后变得更强，而不是更乱？**
   如果没有规则/skills/流程清理与回灌机制，迟早失控。

```
                         |
                         v
                    [B] 规划/分解
                         |
                         v
                +-------------------+
                | [C] 状态/工作流    |
                |  单一运行真相源    |
                +-------------------+
                   |            ^
         选当前任务 |            | 验证结果决定推进/返工/修复
                   v            |
            [D] 上下文装配/记忆 ----+
                   |              |
                   v              |
            [E] 执行 Harness ------+----> [F] 验证/评估
                   |                     (完成裁决闸门)
                   |
                   v
          产出代码/变更/证据/摘要

      [G] 版本/可逆性] = 横切包裹 C + E + F
      [H] 恢复/演进]   = 消费 C + F + 人类反馈，反向更新 A/B/D/F

      [Skills / Rules] = D 的子系统，不是一级控制模块
```
