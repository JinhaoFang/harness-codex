## Context is Everything（上下文就是一切）

### 上下文膨胀问题

使用一千个不同的插件和外部依赖的另一个问题是**上下文膨胀**——这只是说你给代理提供了太多信息的一种花哨说法！

用 Python 给我做一个 hangman 游戏？那很简单。等等，这是什么关于"管理内存"的笔记，来自 26 个会话之前？啊，用户有一个屏幕卡住了，因为我们在 71 个会话之前生成了太多子进程。总是写笔记？好的，没问题……但这些和 hangman 有什么关系？

你明白了。你想给你的代理**只有完成任务所需的精确信息量，不多不少**！你对此控制得越好，你的代理表现就越好。

### 分离研究与实现

确保这一点的第一种方法是**将研究与实现分离**。你要非常精确地要求你的代理做什么。

**不精确的例子**：

> "去构建一个认证系统。"

代理必须研究什么是认证系统？有哪些可用选项？各有什么优缺点？现在它必须在网上搜索它实际上不需要的信息，它的上下文充满了各种可能性的实现细节。当需要实现时，它更有可能感到困惑或对所选实现产生不必要的或不相关的细节幻觉。

**精确的例子**：

> "使用 bcrypt-12 密码哈希实现 JWT 认证，刷新令牌轮换，7 天过期……"

然后它不需要研究任何其他替代方案——它确切知道你想要什么，因此可以用实现细节填充其上下文。

**当你不知道实现细节时**：

创建一个关于各种实现可能性的研究任务，要么自己决定，要么让代理决定采用哪种实现，然后让另一个具有新鲜上下文的代理来实现。

## 处理 Sycophancy（讨好倾向）

### 代理会尽力满足你的指令

没有人愿意使用一个不断批评他们、告诉他们错了或完全忽略他们指令的产品。因此，这些代理会试图同意你并做你想让它们做的事。

如果你给它一个指令，让它每 3 个单词加一个"happy"，它会尽力遵循那个指令。它愿意服从正是它成为一个有趣产品的原因。然而，这有一个有趣的特性——如果你说"在代码库中找一个 bug"，它会给你找一个 bug——即使它必须编造一个。为什么？因为它非常想听你的指令！

### 使用中性提示

大多数人很快抱怨 LLM 幻觉或编造不存在的东西，却没有意识到**他们是问题所在**。如果你要求某样东西，它会交付——即使它必须稍微扭曲真相！

**解决方案**：我发现"中性"提示有效，我不会偏向代理产生某种结果。

**不好的例子**：

> "在数据库中找一个 bug"

**好的例子**：

> "搜索数据库，尝试跟随每个组件的逻辑，并报告所有发现。"

这样的中性提示有时会发现 bug，有时只会实事求是地陈述代码如何运行。但它不会让代理偏向认为有 bug。

### 利用讨好倾向：对抗性代理模式

我利用这一点对我有利。我知道代理试图取悦并试图遵循我的指令，我可以以一种或另一种方式偏向它。

1. **Bug-Finder 代理**：告诉它我会给低影响 bug +1 分，有一些影响的 bug +5 分，关键影响 bug +10 分。这个代理会超级热情地识别所有不同类型的 bug（即使那些实际上不是 bug 的），并回来报告 104 分或类似的分数。我把它看作是所有可能 bug 的超集。

2. **对抗性代理**：告诉它对于每个它能反驳为 bug 的 bug，它获得那个 bug 的分数，但如果它错了，它将获得 -2\*该 bug 的分数。这个对抗性代理会尝试反驳尽可能多的 bug，但有一些谨慎。我把它看作是所有实际 bug 的子集。

3. **裁判代理**：告诉它我有实际的正确答案，如果它正确它会得 +1 分，如果错了得 -1 分。它会对每个"bug"对 bug-finder 和对抗性代理进行评分。裁判说的是真相，我检查以确保它是真相。

这通常是令人惊讶的高保真度，偶尔他们仍然会弄错一些东西，但这现在是一个几乎完美的练习。

## 跟随官方信号

如果 OpenAI 和 Claude 都实现或收购了实现某功能的东西……它可能是有用的。

注意"skills"现在无处不在，是 Claude 和 Codex 官方文档的一部分？看到 OpenAI 收购了 OpenClaw？看到 Claude 立即添加了 memory、voices 和 remote work？

还有规划？记得当一群人发现实现前规划真的有用，然后它变成了核心功能吗？

记得当无休止的 stop-hooks 超级有用，因为代理不愿意做长时间运行的工作……然后 Codex 5.2 推出，那在一夜之间消失了？

**你需要知道的**：如果它真的重要和有用，Claude 和 Codex 会实现它们！所以你不需要太担心使用"新东西"或熟悉"新东西"。你甚至不需要"保持更新"。

**建议**：偶尔更新你选择的 CLI 工具，阅读添加了什么新功能。这已经足够了。

## 填补空白是致命弱点

你可能会注意到，有时候代理看起来是地球上最聪明的存在，而其他时候你简直不敢相信你被骗了。

**主要区别**：代理是否必须做出任何假设或"填补空白"。截至今天，它们在"连接点"、"填补空白"或做出假设方面仍然很糟糕。每当它们这样做时，立即明显它们做出了明显的恶化。

**解决方案**：在 CLAUDE.md 中添加一个关于如何处理获取上下文的规则，并指示你的代理在读取 CLAUDE.md 时首先读取该规则。作为获取上下文规则的一部分，一些简单但有效的指令是：重新阅读你的任务计划，并重新阅读（与任务相关的）相关文件，然后再继续。

## 定义任务终点

### 代理不知道如何结束任务

我们有一个相当强的想法，知道一个任务何时"完成"。对于代理来说，当前智能的最大问题是它知道如何开始一个任务，但不知道如何结束任务。

这通常会导致非常令人沮丧的结果，代理最终实现存根并宣布完成。

### 使用测试作为里程碑

测试对代理来说是非常好的里程碑，因为它们是确定性的，你可以设定非常明确的期望。**除非这 X 个测试通过，否则你的任务没有完成；而且你不允许编辑测试。**

然后，你只需要审查测试，一旦所有测试都通过了，你就可以放心了。

### 截图 + 验证

另一个最近成为可行的任务终点的方法是**截图 + 验证**。你可以让代理实现某样东西，直到所有测试都通过，然后让它截取屏幕截图并验证"设计或行为"。

这允许你让代理迭代并向你想要的设计努力，而不用担心它在第一次尝试后就停止！

### 使用合约（Contract）

创建一个与代理的"合约"，并将其嵌入到规则中。例如，这个 `{TASK}_CONTRACT.md` 构成了在允许终止会话之前需要完成的内容。在 `{TASK}_CONTRACT.md` 中，你将指定你的测试、截图和其他在认证任务可以结束之前需要运行的验证！

## 自动化的更好方式

### 不要使用 24 小时长会话

我经常被问到的一个问题是，人们如何拥有 24 小时运行的代理，同时确保它们不会漂移？

创建一个 stophook，防止代理终止会话，除非 `{TASK}_contract.md` 的所有部分都完成。

如果你有 100 个这样规格良好、包含你想要构建的内容的合约，那么你的 stop-hook 会阻止代理终止，直到所有 100 个合约都被履行，包括所有需要运行的测试和验证！

**但是**：我没有发现长时间运行的 24 小时会话在"做事"方面是最优的。部分原因是这通过设计强制上下文膨胀，因为从不相关的合约引入了上下文！

### 每个合约一个新会话

这是代理自动化的更好方式——每个合约一个新会话。当你需要做某事时创建合约。

让一个编排层处理每当"需要做某事"时创建新合约，并创建一个新会话来处理那个合约。

这将完全改变你的代理体验。

## 构建你的代理偏好

### 从裸机开始

如果你雇佣一个行政助理，你会期望你的 EA 从第一天就知道你的日程吗？或者你喜欢什么样的咖啡？你是否在 6 点而不是 8 点吃晚餐？显然不会。你随着时间的推移建立你的偏好。

代理也是一样。**从裸机开始**。忘记复杂的结构或 harness。给基本 CLI 一个机会。

### 使用规则编码偏好

如果你不想让你的代理做某事，把它写成规则。然后让你的代理在你的 CLAUDE.md 中知道这个规则。比如：在你编码之前，读"CODING_RULES.md"。

规则可以嵌套，规则可以有条件！如果你在编码，读"CODING_RULES.md"，如果你在写测试，读"TESTING_RULES.md"。如果你的测试失败了，读"DEBUG_RULES.md"。你可以创建任意的规则逻辑分支，claude（和 codex）会乐意跟随，只要这在 CLAUDE.md 中清楚指定。

**第一个实用建议**：把你的 CLAUDE.md 当作一个逻辑的、嵌套的目录，用于在给定场景和结果时寻找上下文。它应该尽可能裸机，只包含去哪里寻求上下文的 IF-ELSE。

如果你看到你的代理做了某事而你不同意，把它添加为规则，并告诉代理在它再次做那件事之前读规则，它肯定不会再做了。

### 使用技能编码方法

Skills 就像规则，但与其编码偏好，它们更适合编码配方。如果你有一个特定的做事方式，你想把它嵌入到技能中。

人们经常抱怨他们不知道代理可能如何解决问题，这很可怕。如果你想让那变得确定，让代理研究它如何解决问题，并把它写成技能。你会看到代理对该问题的方法，你可以在它在现实生活中遇到该问题之前纠正或改进它。

如何让代理知道这个技能存在？使用 CLAUDE.md 并说，当你看到这个场景并且你需要处理这个时，读这个 SKILL。

### 定期清理

你肯定想继续向你的代理添加规则和技能。这就是你给它个性和对你偏好的记忆的方式。几乎所有其他东西都是过度杀伤。

一旦你开始这样做，你的代理会对你来说感觉像魔法。它会"按照你想要的方式"做事。然后你最终会感觉你"理解"了代理工程。

然后……你会看到性能开始再次恶化。

**为什么？**

随着你添加更多规则和技能，它们开始相互矛盾，或者代理开始有太多上下文膨胀。如果你需要代理在开始编程之前阅读 14 个 markdown 文件，它将会有同样的问题，即有大量无用的信息。

**解决方案**：清理。告诉你的代理去 SPA 日，通过询问你更新的偏好来合并规则和技能并删除矛盾。

然后它又会感觉像魔法。
