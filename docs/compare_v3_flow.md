# Agentic 架构合并评估报告：v3 与 Flow

## 🎯 一、 总判断：互补而非替代

这两个项目在架构设计上处于不同的层级，最合理的协作模式是：**`v3` 主内（治理真相），`flow` 主外（交付协作）。**

- **`v3` (Agentic Codex Runtime v3)：上层运行时宪法与治理模型**
  - **核心：** 承接“三层真相 + 六项总纲 + 控制面分治”的设计。
  - **定位：** 管控 Agent 内部执行的逻辑真相与治理规则。
- **`flow` (Coding-Agent-Flow)：下层交付流程模板**
  - **核心：** 建立 `Harness → PRD/API/UI → 测试用例 → TDD → GitHub → Review` 的生产线。
  - **定位：** 驱动 Agent 进行外部的交付与团队协作。

## 📊 二、 核心机制对照矩阵

| 维度                  | `v3` (偏向：运行时治理)                                                                       | `flow` (偏向：交付流水线)                                                              |
| :-------------------- | :-------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| **AGENTS.md 定位**    | **薄宪法 + 路由入口 + 控制面**                                                                | **团队操作手册**，默认启用 Harness/GitHub/TDD 闭环。                                   |
| **真相模型 (Truth)**  | **严格切分对象所有权**，显式区分：目标真相 / 过程真相 / 世界真相 / 过程证据。                 | **无同级别本体切分**，由 PRD/API/UI、测试用例、Issue/PR 等共同承载信息。               |
| **门禁机制 (Gate)**   | **极严**。核心是 `DISCUSS -> PLAN` 门禁，未达到 95% 理解及 Plan Review 未通过，绝不允许实施。 | **流程约束**。流水线式的“先文档、后测试、再实现”，要求各环节与 Issue/PR 强绑定。       |
| **技能设定 (Skills)** | **窄而硬的“阶段节点技能”**（如：对齐世界、冻结计划、独立审查、捕获证据等）。                  | **宽泛的“生产线技能”**（涵盖需求分析、TDD 开发、PR 处理、工作区管理等）。              |
| **模板 (Templates)**  | **运行时模板**（如 `plan.md`, `workflow.md`, `review.json`, `evidence.json`）。               | **交付物合同模板**（如 PRD、API/UI 规范、测试原则、Issue 模板）。                      |
| **核心工具 (Tools)**  | `agentctl.py` 是真正的**确定性控制面**（包含计划完整性校验、门禁校验、证据写回等）。          | `harness.py` 目前偏向**状态队列脚本**（处理初始化、声明、更新进度、完成/失败等状态）。 |
| **规范与工具对齐**    | 严格对齐。                                                                                    | 规范承诺较多（如会话恢复、检查点、回滚），但 `harness.py` 工具中大多未实质落地。       |
| **角色划分 (Roles)**  | **按“治理职能”划分**（探索者、执行者、计划审查员、结案审查员等），强调审查独立性。            | **按“软件生命周期(SDLC)”划分**（产品经理、QA、开发者、代码审查者等）。                 |
| **代码审查 (Review)** | **绝对独立**。要求独立的计划审查和结案审查，**Reviewer 绝不能自行修改代码**。                 | **混合操作**。Review 技能中允许“审查 + 修复 + 合并”一条龙（与 v3 的边界冲突）。        |
| **完成定义 (Done)**   | **显式单点定义**。必须有全新的上下文包、真实验证、证据落地、独立评审通过。                    | **流程闭环推导**。没有同级的单点定义，更多依赖 Harness + PR + CI 的组合来确认。        |

## 🚫 三、 架构红线（绝对不可引入）

在整合过程中，以下 `flow` 的做法会破坏 `v3` 的底层逻辑，**必须严守底线**：

- ❌ **拒绝“单一事实来源”：** 绝不能让 `AGENTS.md` 成为唯一的真相来源。这会直接摧毁 `v3` 精心设计的“分权真相模型”（Plan/Workflow/Code/Evidence 分离）。
- ❌ **拒绝 GitHub 越权：** 绝不能将 GitHub Issue/PR 设定为流程的必经门禁（Gate）。GitHub 只是外部协作面和证据池，**绝不是单一事实来源 (SoT)**。
- ❌ **拒绝日志越权：** 绝不能将类似 `harness-progress.txt` 的会话日志升格为“真相层”，在 `v3` 中它最多只能算作临时执行状态或过程证据。
- ❌ **拒绝破坏独立评审：** 坚决抵制 `gh-pr-review` 中“Reviewer 顺手修代码并合并”的模式，必须捍卫“既当裁判就不能当运动员”的独立评审底线。
- ❌ **拒绝不安全配置：** 严禁将 `flow` 中的高危配置带入 `v3`（例如：免审批执行 `approval_policy="never"`、默认开放网络、以及 Harness 协议中破坏性的回滚机制）。
